# Что нужно для действующего API

Зелёный `/health` означает, что процесс отвечает, а не что оплаченный провайдер
доступен. `/v1/models` показывает настроенные модели, даже если upstream-ключ ещё
не подключён. Без доступного ключа обычный запрос completion возвращает 503.

## Обязательные внешние условия

- Сервер с Docker Compose v2 и доступом к API выбранного провайдера.
- Домен с DNS на сервер, открытые порты 80/443 для Caddy и выпуска TLS-сертификата.
- Разрешённый провайдером API-ключ с доступом к нужной модели и действующей квотой.
- Разные `ADMIN_API_KEY` и `GATEWAY_API_KEY`, переданные через секреты окружения.
  Не вводите их в чат, команды с литеральными значениями, Git или CI-логи.
- `PUBLIC_DOMAIN` — домен без схемы; `PUBLIC_ORIGIN` — HTTPS origin клиента.
  Origin GitHub Pages уже добавлен в конфигурацию отдельно.

Production-конфиг не запускается без админ-ключа, с одинаковыми клиентским и
админским ключами или с нераскрытыми переменными в списках ключей. Если выдача
клиентских ключей отключена (`public_api.enabled: false`), нужен статический
клиентский ключ. При включённой выдаче его можно не задавать.

## Подключение провайдера

Выберите поддерживаемую вашим аккаунтом модель и обновите `providers[].models`,
`default_model` и маршрутизацию в `config.production.yaml`. Список в репозитории —
пример, а не гарантия текущей доступности моделей у провайдера. Отключите ненужных
провайдеров.

Существующий production-профиль читает операторские ключи из переменных с префиксами
`OPENAI_TOKEN_`, `ANTHROPIC_TOKEN_`, `GOOGLE_TOKEN_` внутри контейнера. Передайте их
через защищённую конфигурацию развёртывания. Compose также читает локальный `.env`
на сервере: он должен находиться вне Git, с ограниченными правами доступа. Произвольные
переменные shell с этими префиксами сами по себе не передаются в контейнер — их нужно
явно передать через среду контейнера или серверный env_file. Альтернатива — ручной
импорт своего разрешённого ключа через `POST /admin/tokens` по HTTPS.

Redis содержит upstream-ключи, необходимые для запросов. Он не публикуется наружу;
защитите сервер, Redis volume и резервные копии. Не считайте хеширование клиентских
ключей шифрованием upstream-хранилища.

## Запуск и приёмка

На сервере, после настройки секретов:

```sh
docker compose config --quiet
docker compose up -d --build --wait
docker compose ps
```

Не запускайте `docker compose config` без `--quiet` в общедоступных логах: вывод
может содержать развёрнутые значения переменных.

Проверьте по публичному HTTPS-адресу:

1. `GET /health` → 200.
2. `GET /v1/models` без ключа → 401.
3. Выпуск клиентского ключа через панель → зашифрованный файл.
4. `POST /v1/chat/completions` с клиентским ключом → 200 и настоящий ответ модели.
5. Тот же запрос с `stream: true` → SSE, завершающийся `[DONE]`.
6. `GET /v1/usage` → учёт токенов.
7. После перезапуска gateway выпущенный ключ продолжает работать (Redis).
8. После отзыва ключа запросы им отклоняются.

Вызовы внешней модели могут расходовать платный баланс. Установите лимит бюджета
в кабинете провайдера до приёмки. Автоматического получения новых free-tier аккаунтов
или пополнения чужих квот нет.

## Что уже проверяется автоматически

- Локальный HTTP upstream fixture: настоящий pool/adapter, обычные ответы и SSE,
  авторизация, перевод имени модели, учёт токенов и отзыв клиентского ключа.
- Chromium: выпуск ключа через панель, шифрование и скачивание.
- GitHub Actions: сборка Docker, admin Compose и HTTP smoke-тесты.

Тестовый upstream не является языковой моделью. Эти проверки не доказывают
доступность реального провайдера, публичного DNS/TLS или сохранность production Redis
после перезапуска — такие проверки выполняются на целевом сервере.
